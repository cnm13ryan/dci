# DCI v15: notebook → portable codebase — migration report

Everything in this document is grounded in one of four evidence classes and
labelled where it matters: **[impl]** behavior demonstrated by the executable
v15 implementation or by this repository's test runs; **[v15-doc]** a
requirement stated in the v15 documentation; **[ext]** an external
software/platform fact from a primary source; **[rec]** an engineering
recommendation. Proposed scientific changes: none — this migration makes no

## A. Source audit

The notebook is 33 executable cells sharing one kernel namespace, already
factored by topic. `docs/migration_map.csv` (generated by the migrator) maps
every cell to its stage module with its shared-state reference count and
injected library imports. Classification:

| kind | cells | destination |
|---|---|---|
| pure scientific logic | verifier rules, statistics kernel, audit sizing, hashes, statuses, exceptions, constraint spec, estimand declarations | extracted libraries (84 defs), unit-tested imports |
| stateful orchestration | the gate cells (222–402), calibration loop, screening, freeze, export | stage modules over explicit shared state `S` |
| platform-specific | Colab/Drive mount, `%pip` cell, torch/transformers imports | storage adapter, environments/, compat shim |
| model inference | cell 132 (load/free/fingerprint), cell 192 torch branch | `dci/inference/hf_transformers.py` |
| dry-run oracle | cell 192 synthetic branch | `dci/inference/oracle.py` |
| analysis/plotting | 362–412 | stages (figures use Agg; display shim) |

Scientific invariants constraining the refactor: the 23 listed in the
migration specification, all of which live in executable code the migration
carried over unchanged — the migrator's guarantee is textual (cell bodies are
byte-identical apart from the S-rewrite and eight ledgered patches), and the
regression suite is the behavioral proof. **[impl]**

## B. Target architecture

```
profiles (TOML, class A+B selectors)         configs/profiles/*.toml
        │  loader.ACTIVE (class B: backend, device, shard, data_root)
        ▼
runner ──imports stages in cell order──▶ stages/c112…c412
        │                                   │ S.<name> (class C run state,
        │                                   ▼  263 names, all greppable)
        │                              dci/pipeline/state.py
        │ exit taxonomy: 0/10/20/30/1       │
        ▼                                   ▼
stop.json / artifacts            libraries (pure, unit-tested)
                                 inference backends (oracle | hf_transformers)
                                 storage layout + durable journal
                                 provenance (fingerprint, hardware class)
```

Local/cloud boundary: identical source tree and identical class-A protocol;
class-B execution differs (ROCm vs CUDA environment, device, storage root) and
is recorded in provenance; class-C state never crosses the boundary — code and
configuration migrate, generation caches do not, and the hardware-class check
plus the execution fingerprint make the forbidden cache migration structurally
refused, not merely discouraged. **[impl]**

Why explicit shared state instead of full dataflow decomposition now: the
notebook's semantics ARE one namespace with late binding; any Stage-A rewrite
into parameter passing would have had to re-derive several hundred def-time vs
call-time binding decisions by hand, each one a silent-divergence risk against
110 assertions. `S` reproduces those semantics exactly, makes every shared
name auditable, and leaves incremental de-globalization as ordinary refactors
that the regression suite can police one name at a time. **[rec]** The migrator
itself (symtable-scoped rewriting, f-string-safe splicing, purity-checked
extraction) is in `tools/migrate_v15.py` and re-runs reproducibly.

## D. Reproducibility report (spec deliverable I)

Baseline facts reproduced **exactly** [impl]:

* Gate 0: **110 passed / 0 failed** (CLI `--until c222`, and inside every full run).
* Full `dev_fast` dry run: gate trace identical to the notebook fixture
  (10 GATE lines, statuses and bypass flags), `ALL STAGES EXECUTED`.
* **38 deterministic artifacts byte-identical** after stripping volatile
  identity fields (timestamps, run ids, wall-clock, machine paths): every gate
  CSV/JSON, calipers, calibration signature, sensitivity diagnostics, τ
  matrix, primary effects, claim rule, protocol fields. Comparator:
  `tests/regression/compare.py`; zero values needed the 1e-9 tolerance —
  exactness held everywhere.
* `integration_pass`: Gate 0 → PASS, Gate M → PASS, Gate 1 → PASS, Gate 2a →
  PASS, Gate 2 → `NOT_IDENTIFIED_SUPPORT`, **zero bypasses**, exit 10. This
  stop is the expected baseline result and the port treats it as success.
* Failure-path statuses with their remedy flags (AUDIT_MISSING,
  U_PRECISION_INSUFFICIENT, PRECISION_INSUFFICIENT, NOT_IDENTIFIED_SUPPORT,
  REFERENCE_VALIDATION_NOT_EVALUABLE/FAILED, WORDING_VALIDATION_FAILED,
  FINAL_FALSIFICATION_FAILED) — identical JSON after volatile stripping.

Changed **by documented necessity** (ledger `L-hash-relocation`): the five
source-fingerprint protocol fields and therefore `plan_sha256`
(`e92c6d01…` → `49b5012e…`). They hash source text; the text moved. Forging
the old values would be false provenance, so the new identity is pinned and
the comparator fails if any *other* field drifts. Consequence: notebook-era
run directories are not resumable by the package (correct refusal).

Impossible to compare here **[env]**: real-model generation (this container
has no GPU stack — deliberately, which is itself the proof that the scientific
core runs torch-free), ROCm and CUDA doctor GPU tiers, Lambda API calls, and
`uv.lock` generation against repo.radeon.com (locks must be produced on the
target machines; instructions are in `environments/*/README.md`).

External facts verified for the environment definitions **[ext]**: AMD's
current matrices list PyTorch 2.9.1 ↔ ROCm 7.2.1 as the officially supported
pairing on Radeon, with the RX 7900 XTX (gfx1100) supported on Ubuntu
24.04.4/22.04.5 (AMD ROCm docs, checked 2026-08-09); the exemplar project's
rocm-rel-7.2 wheel pins match that matrix. Lambda API/behavioral facts follow
the attached runbooks, themselves checked against live Lambda docs 2026-07/08.

## E. Remaining blockers (spec deliverable J)

* **Engineering** — vLLM backend: not implemented; adding it is a new
  `CFG.engine` value requiring parity tests and a deliberate freeze (Phase-9+
  work). Deeper de-globalization of `S` (incremental, regression-policed).
* **Environment** — must run on the real machines: `uv sync` + `local_doctor
  --gpu --expect-devices 2` on the workstation (Phase 7–8); Lambda bootstrap +
  `cloud_doctor` on an instance (Phase 9). This sandbox cannot reach GPU
  stacks or generate the two locks.
* **Compute** — Phase 8 measurements (VRAM/throughput/latency on 7900 XTX),
  Phase 10 cloud pilot from a clean state, then the frozen study invocation:
  `dci run --profile study --data-root /lambda/nfs/<fs>/dci --run-id study-v15 --execute`
  (refused until both audits are signed — Gate M enforces it).
* **Scientific (unchanged, still open)** — the six `v15_open_questions.md`
  items: κ's causal role, the additive joint-budget bound, per-implementation
  5% certificates, 3/4/4 sufficiency, pilot-informed N, transport-failure
  interpretation. Also still true from v15: the no-bypass traversal past Gate
  2 requires a fixture with more precisely measured incoming-vulnerability
  components; the transport module remains declared-but-unimplemented; the
  53-field behavioral audit still covers the 14 fingerprint fields.
