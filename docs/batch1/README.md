# DCI Batch 1: instruction library, independent pilot calibration, reference selection

Implementation report. The code is `src/dci/batch1/`, the tests are
`tests/batch1/`, and every other file in this folder is generated by
`python -m dci.batch1 write-review-artifacts` (a test fails when one is stale).

**Reviewer? Start at [`RESEARCHER_REVIEW.md`](RESEARCHER_REVIEW.md).**

**Status: implemented, independently audited twice (2026-10-19), remediated
after both, and validated on CPU with synthetic data. Nothing has been run on
a model.** No pilot generation, no composed outcome, no GPU
work. The pilot protocol is not authorised: all 14 decisions in
[`decisions.md`](decisions.md) are `PROPOSED`, and the execution environment
is not attested. What the audit found and what changed is in
[`REMEDIATION_REPORT.md`](REMEDIATION_REPORT.md); how reliable the pilot's
memberships and verdict are, by simulation, is in
[`CALIBRATION_PRECISION_REVIEW.md`](CALIBRATION_PRECISION_REVIEW.md).

## 1. What Batch 1 does

The pilot measures stand-alone compliance only:

- the task alone;
- the task plus one A count;
- the task plus one B limit;
- the task plus one of the 51 candidate references.

From these it selects:

- one global A count;
- two global B limits;
- the 20% eligible pool and the separate 10% extension;
- the B-specific compatible libraries;
- G1–G6 with hierarchical weights for every model × frame × B configuration;
- support for P1–P3.

All of this is hash-bound in Freeze 2, before any composed prompt exists. The
package cannot render a composed prompt: the template has one instruction line,
and `Cell` and `render_prompt` refuse a second constraint. Before anything is
generated, every requested row is compared field by field with the design
regenerated from Freeze 1, and the instruction lines are counted in the prompt
bytes, so a hand-edited design row cannot smuggle a second instruction past a
`load: 0` label (audit F5).

## 4. The library

The library has 51 references in 7 operation classes. The full list, with both
wordings, verifier, vacuity rule and compatible B limits for each, is in
[`library_review.md`](library_review.md); the machine-readable version is
[`library_manifest.json`](library_manifest.json).

| operation | object | variants | proposed parameters (D01) |
|---|---|---|---|
| exact_count | word | 22 | the design's grid: 8 words × {2, 4, 6}, nonetheless and consequently {2, 4} |
| exact_count | punctuation | 4 | commas 3, 6; semicolons 1, 2 |
| exact_count | sentence | 2 | 4, 7 sentences |
| exact_count | paragraph | 2 | 2, 3 blank-line-separated paragraphs |
| required_inclusion | word | 4 | *simple*; *window* and *garden*; *silver*, *morning* and *quiet*; *remarkable* (10 letters) |
| prohibition | word | 2 | *the*; *very*, *really* or *just* |
| prohibition | letter | 2 | z; b |
| numerical_bound | sentence | 3 | every sentence ≤ 20 words; ≤ 12; ≥ 10 |
| uniqueness | word / word_sequence / sentence | 3 | no word of ≥ 5 letters twice; no repeated word pair; ≥ 3 sentences with distinct first words |
| ordering | sentence | 4 | ≥ 4 sentences with increasing word counts; ≥ 4 decreasing; ≥ 4 first words in strict alphabetical order; ≥ 6 increasing |
| relational_dependency | sentence_pair | 3 | ≥ 3 sentences: each starts with the previous sentence's last word; with its last letter; shares a ≥ 4-letter word with it |

Every ordering and relational variant states its minimum sentence count in the
wording, and the verifier requires it, so a one-sentence answer cannot pass.

The two frames are:

- **F0, imperative:** "Use…", "Write…", "Do not…".
- **F1, requirement:** "Your answer must…".

A's strings are v8.1's A frames 0 and 1; B's are the historical B wordings 1
and 0. A test checks that both frames render every parameter. The verifier never
sees the frame.

### Text semantics (D03)

These are the historical B verifier's semantics, inspected and kept:

- **Word:** a maximal run of `str.isalpha` characters in the raw response
  (`alpha_runs`, a byte-identical copy).
- **Apostrophes and hyphens** split words: *don't* is *don* + *t*.
- **Digits** are not letters.
- **Accented and non-Latin letters** count as letters.
- **No Unicode normalisation.**
- **A zero-width space splits a word.** This is historical and could be gamed
  under B. It is kept for the primary verdict, and every scored row records
  `format_characters` so any use is visible.
- **Comparisons:** each word is folded after segmenting. This differs from
  historical A's fold-first S0 only on U+0130, as a test shows.
- **Sentences:** split per line with the certified v19 boundary and abbreviation
  guard, so a heading or list item is a sentence.
- **Paragraphs:** blocks of non-blank lines separated by blank lines.

### Outcomes and compliance (D04)

Every backend row is classified first (`outcomes.py`):

- **VALID:** generated, with visible text. It is scored; truncation is kept.
- **EMPTY:** a completed generation whose answer is blank. Under NO_THINKING,
  the vLLM seam writes this as `CHANNEL_INVALID`. It is read as EMPTY only
  when the row shows no reasoning, blank raw text and a completed decode.
  EMPTY rows are in every denominator, never comply, and are not regenerated.
- **TECHNICAL:** no completed generation. This covers capacity failures,
  unsupported backends, crashes, rows never returned, and any
  `CHANNEL_INVALID` the empty rule cannot explain. These rows are never
  evidence: they are logged in `rejected.jsonl` and the request stays open
  for `resume`.

A response complies when all four hold:

1. the verdict is PASS;
2. it is not empty;
3. it is not truncated;
4. it is non-vacuous.

Prohibition, uniqueness, bound and B rules also need at least 20 words, the
historical floor. A PASS that is not compliance records its reason: vacuous,
truncated or empty. So both of these can be recovered from the stored records:

- literal compliance (the verdict);
- the primary non-vacuous measure.

`refusal_like` (a phrase list) and `structure_lines` (markdown structure) are
diagnostics only.

## 5. Compatibility

The matrix covers 54 constraints × 6 B limits: the 51 references and the 3 A
counts. Of the 324 cells, 305 are compatible, 19 incompatible and **0
unresolved**. See [`compatibility_review.md`](compatibility_review.md).

- **Incompatible cells.** Each one carries a proof: the rule forces a word longer
  than m. The affected references are:
  - *therefore* at B8;
  - *nonetheless* at B8–10;
  - *consequently* at B8–11;
  - *remarkable* at B8–9.
- **Compatible cells.** Each one stores a constructed witness that is compliant
  under both verifiers.
- **Task level.** Each of the 305 compatible cells also has a witness that
  meets the prompt's 60–120-word contract and is compliant under X and B
  (64–93 words; `task_level` in the matrix). That is logical satisfiability
  of the full response contract, not followability.
- **Library size by limit:** compatible references number 43, 46, 47, 49, 51
  and 51 at B8 to B13.

Unresolved cells are refused at the freeze. The selection code never restricts to
the common-compatible subset.

## 6. Pilot protocol (D05, D06, D12)

**Topics.** There are 576 new questions, 48 in each of the historical twelve
areas.

- **Overlap check (revised after audit F4).** The bank is compared with every
  historical DCI bank in the repository: 2,096 questions from v2, v3, v3's
  candidate list, v4, the v5–v7 calibration banks and the v15/v19 task bank,
  plus 192 sequestered hashes.
  - **The screen:** word-set Jaccard ≥ 0.5 or stemmed content-word Jaccard ≥
    0.3. Every flagged pair needs a recorded review decision.
  - **The result:** 42 questions were rewritten under their topic ids, so the
    split did not move. Of these, 36 restated a historical question and 6
    contained a library target word. 37 flagged pairs were judged distinct,
    each with a rationale.
  - **Re-audit (R1):** paraphrases that share no words escaped the screen. 88
    more questions were rewritten after a semantic review of the whole bank,
    and a rare-word screen was added. See [`TOPIC_REVIEW.md`](TOPIC_REVIEW.md).
  - See [`topic_screen_report.md`](topic_screen_report.md), `topic_overlap.json` and
    `topic_hygiene.json`.
- **Split:** by a fixed seed, 8 questions per area go to the pilot (96) and the
  other 480 are reserved for confirmation. No Batch 1 code path reads the
  reserved set.
- **Stages:** of the 96 pilot topics, 32 are Stage 1 and 64 are Stage 2.

**Stage 1.** Each of the 480 stand-alone cells gets one response on each of the
same 32 topics. The cells are 4 models × 2 frames × (3 A + 6 B + 51 X). Task-only
gets 32 topics × 2 draws per model; its prompt contains no instruction, so it is
generated once per model. Total: 15,616.

**Stage 2 (proposed rule).** One bounded round of at most 240 cells, each with 64
new-topic responses, so at most 15,360 more.

- **Candidates:** a cell whose Stage 1 interval straddles a decision boundary.
- **Ranking:** by class, in this order:
  1. A headroom band edge;
  2. B informative band edge;
  3. 20% eligibility;
  4. ±10 pp matching against any A count;
  5. 10% extension.

  Within a class, cells nearest the boundary come first, measured in boundary
  standard errors; ties break on the cell key.
- **Why eligibility outranks matching:** with three A counts, matching
  candidates alone filled the cap and starved eligibility in the synthetic test.
- **Completeness gate (audit F2).** The selection is computed only when every
  Stage 1 design row has exactly one accepted generation and one score derived
  from it. It records the hash of that evidence. Planning, executing and
  finalising Stage 2 recompute it and refuse a mismatch, so a partial, edited
  or re-scored Stage 1 cannot feed Stage 2. Finalisation needs both stages
  complete.
- **No third stage.**

**Seeds** are a function of the following, and never of batch position:

- domain and root (`202610180`);
- stage;
- model id and revision;
- prompt hash;
- draw.

**Decoding** is v8.1's. The proposed cap is 512 tokens.

## 7. Selection rules

These are the design values; operational details are listed as D07–D11.

- **Eligibility.** A candidate qualifies if its raw point estimate is at least
  20% in any model-frame, compared in exact rational arithmetic; it is then in
  every model's pool.
  - Candidates that qualify only at 10% are `EXTENSION_ONLY`, a separate
    sensitivity population.
  - A candidate with no qualifying cell and an incomplete cell is
    `UNDETERMINED`.
  - Wilson intervals are reported, and each decision is marked clear or
    borderline.
- **Matching.** |p_X − p_A| ≤ 0.10, per model and frame, never pooled. The
  Newcombe interval of the difference is reported, along with whether it lies
  entirely inside ±0.10.
- **Chance correction.** iota = (p − κ)/(1 − κ), with κ the task-only rate
  for that model. When κ = 1, iota is undefined: the reference is unmatched and
  flagged. B-only spontaneous compliance is a separate table and is never used
  as κ.
- **B selection (D07, revised).** A pair m1 < m2 is admissible only when:
  - m2 − m1 ≥ 2, and every cell is complete;
  - the median B-only compliance over model-frames rises by at least 0.15;
  - that separation holds in at least 3 of the 4 models;
  - each limit is informative ([0.15, 0.85]) in at least 4 of 8 model-frames.

  Admissible pairs are ranked by informative cells, then the worse limit, then
  the separation. If no pair is admissible, B selection FAILS and nothing is
  selected.
- **A selection (D08, revised).** An N is admissible only when p_A is in
  [0.10, 0.90] in at least 6 of 8 model-frames, across at least 3 models.
  - **Ranking:** among admissible counts, by configurations with G1 support
    and an informative A, then headroom, then N = 4, then the smaller N.
  - **Uninformative A:** a configuration whose A is outside the band is
    reported but never counts toward feasibility.
  - **No admissible N:** A selection FAILS (`A_HEADROOM_INADEQUATE`). There
    is never a per-model fallback.
  - **Short of the target:** an admissible choice that falls short of the
    target is flagged `A_COVERAGE_INADEQUATE`.
- **Populations and weights.** G1–G6 are built as in the brief from the
  eligible, B-compatible pool, excluding A, and nesting is asserted.
  - Weights are equal over operations, then over object types within an
    operation, then over variants. They are exact fractions and sum to one.
  - Membership takes no prompt-order input.
- **Coverage (D11).**
  - G1 needs at least 3 distinct target words.
  - P1 needs G2 to add at least 2.
  - P2 needs G3 to add at least 2 of another object type.
  - P3 needs G5 to add at least 2 of another operation, and (proposed) G3 to
    hold at least 3.
- **Reasons for unsupported comparisons.** Each one names the filter that bit:
  library, eligible, compatible, or matched. A relaxation that adds nothing is
  reported as `NO_EFFECTIVE_POPULATION_EXPANSION`.
- **Feasibility target.** At least 12 of 16 configurations, at least 3 models,
  and both B limits, for each contrast. Only configurations whose A is
  informative count.
- **Stability (D14, proposed, diagnostic only).** A topic-cluster bootstrap
  reports:
  - each reference's inclusion frequency;
  - the A, B and FEASIBLE shares;
  - borderline matches;
  - a Stage-1-only sensitivity;
  - P1–P3 recomputed on stable members.

  `FEASIBILITY_RESTS_ON_UNSTABLE_MEMBERS` is raised for review. It is not a
  gate, and membership is never changed by it. The precision review shows
  it cannot reliably tell true from false FEASIBLE verdicts.

## 8. Freezes and authorisation

**Freeze 1** (`freeze1_proposed.json` is the current proposal) hashes the
following:

- the configuration;
- every constraint specification;
- the verifier bundle and text semantics;
- the logical and full-length compatibility results;
- the topic bank, its split, and the overlap and hygiene reports;
- the models, decoding and prompts;
- the Stage 1 design digest (every field that decides a generation);
- the code of every package module that generates, scores, gates or selects,
  plus `dci/verifiers/rules.py` and `dci/provenance/hashes.py`. These are
  code hashes, so editing a docstring or comment changes nothing;
- the vLLM seam source;
- the execution-environment lock;
- the seed derivation;
- the decision register.

`validate-freeze` recomputes all of it and lists every mismatch. Tests show that
editing the manifest, a topic, a threshold or a rule module is detected.

**Authorisation.** Real generation needs all of the following:

- a Freeze 1 that validates;
- every decision `APPROVED` in `approvals.json`, against its current payload
  hash, with a name and date. Each payload binds its implementing code, so
  editing selection code voids exactly the approvals it implements;
- an environment lock from `attest-environment` on the generation host
  (interpreter, vLLM, torch and transformers versions, the hash of every
  installed distribution, the accelerators, the seam source);
- a live environment identical to that lock, re-probed at `execute`;
- `--authorize <manifest hash>`.

The code never writes `APPROVED` and never fabricates an environment. On this
Mac, Freeze 1 records `UNATTESTED`.

**Freeze 2** binds the evidence itself:

- per stage, the design digest, the hash of every accepted response record
  and of every full score vector, the outcome classes, and the technical
  attempts, which are kept apart;
- the Stage 2 selection and the Stage 1 evidence it read;
- the pooled tables;
- the calibration;
- the D14 diagnostics.

`validate-freeze` rebuilds it from the run root and re-scores every response,
so an edited response, a flipped verdict or a duplicated row is detected.
Three further rules:

- Freeze 2 records that no prompt carried more than one instruction, read
  from the prompt bytes;
- an infeasible result freezes as `REVISION_REQUIRED`;
- synthetic evidence cannot be frozen as pilot evidence.

## 9. Commands

```bash
P=".venv/bin/python -m dci.batch1"
$P validate-library                  # 51 variants, 7 operations, design counts
$P validate-verifiers                # witness/violation/empty/truncation self-check
$P check-compatibility               # the 54 x 6 matrix; exit 1 if any unresolved
$P estimate                          # counts, storage, historical-rate runtime
$P write-review-artifacts            # regenerate docs/batch1/*
$P demo --root "$(mktemp -d)/demo"   # full-size synthetic pilot, about 90 s on CPU

# On the generation host, before Freeze 1
$P attest-environment --backend-python PATH --out environment_lock.json
$P smoke-plan                        # prints the smoke plan hash (<= 96 rows)
$P smoke --root S --authorize <smoke plan hash> --max-rows 96 \
         [--accelerator cuda] [--backend-python PATH]   # never pilot evidence

# The real pilot, after approval (R = an empty run root)
$P freeze-protocol   --root R --approvals approvals.json \
                     --environment-lock environment_lock.json
$P validate-freeze   --root R
$P plan              --root R --stage stage1
$P execute           --root R --stage stage1 --authorize <freeze1 hash> \
                     [--accelerator rocm|cuda] [--devices 0,1] [--backend-python PATH]
$P resume            --root R --stage stage1 --authorize <freeze1 hash>   # same, idempotent
$P status            --root R        # completeness and open technical failures
$P score             --root R --stage stage1
$P select-refinement --root R        # writes the Stage 2 plan
$P execute           --root R --stage stage2 --authorize <freeze1 hash>
$P score             --root R --stage stage2
$P finalize-calibration --root R     # = construct-references; writes reference_selection.md
$P report-coverage   --root R
$P freeze-membership --root R
$P validate-freeze   --root R        # now checks Freeze 2 too
```

`execute` exits 3 and launches nothing (all tested) when any of these hold:

- `--authorize` is missing;
- any decision is unapproved;
- the environment is unattested or has changed;
- a design row differs from the frozen design;
- Stage 1 is incomplete, for a Stage 2 run.

It exits 4 when generation ran but technical failures remain open; `resume`
retries them. `--synthetic` swaps in the CPU stand-in and marks the run root
synthetic.

## 10. Compute estimate

See [`estimate.md`](estimate.md).

- **Stage 1:** 15,616 generations.
- **Stage 2:** at most 15,360.
- **Total:** at most 30,976.
- **Storage:** at most about 250 MB. The synthetic run measured about 3.4 KB
  per scored row and 0.8 KB per design row.

At the v8.1 rates on one RX 7900 XTX (17.4, 10.1, 9.7 and 4.94 rows/s), Stage 1
is about 0.5 card-hours and Stage 2 at most 0.65, plus 2–5 minutes of model
load per backend run. These are historical rates, not measurements of any other
hardware.

Before a cloud estimate means anything, the authorised smoke test (`smoke`,
at most 96 rows, its own namespace, no compliance computed) must measure, per
model on the chosen instance, at this cap and a chunk size of 64:

- rows per second;
- model load time;
- truncation share;
- backend health.

The precision review recommends no increase in the allocation, so the counts
are unchanged.

On NVIDIA (D12, 2026-10-25) the backend is `environments/cuda-vllm`: Python 3.12, vllm 0.15.1 (cp38-abi3) and torch 2.9.1+cu129 from the explicit cu129 index, locked for Linux x86_64. `execute --accelerator cuda --devices 0,1` runs one worker per GPU, each seeing only its own device through `CUDA_VISIBLE_DEVICES`, with TP as configured (1). The environment lock binds the software and the GPU class (model, count, compute capability, memory) and records the hostname, kernel, GPU UUIDs and driver without binding them; a host outside D12's execution requirements cannot be locked or frozen. `scripts/lambda/` holds the host scripts. It has not been built, attested or smoke-tested on the instance yet.

## 13. Known limitations

- **Topics.** An agent drafted the questions and revised 42 of them; neither
  the bank nor the review decisions have had the researcher's review.
- **Witnesses** prove satisfiability. They are pool-built, and many are word
  salad rather than prose.
- **Calibration precision.** At pilot sample sizes, a reference within 0.05
  of the ±0.10 edge is misclassified about 40% of the time under every
  affordable allocation. Minimum-count coverage is anti-conservative near
  the 12-of-16 threshold (simulated; see the precision review). D14 reports
  instability but cannot detect or remove the bias.
- **Uncertainty.** Wilson and Newcombe intervals treat responses as
  independent. D14's topic bootstrap does not.
- **κ is per model** and is used for both frames.
- **Alphabetical order** compares folded words by code point.
- **Approvals are plain JSON,** protected by payload hashes that bind code,
  not by an HMAC signature as v8.1's records were.
- **The CUDA vLLM backend** (`environments/cuda-vllm`) is locked but has not been built, attested or smoke-tested on the instance.
- **Synthetic results are not evidence.** The demo reaches `FEASIBLE` because
  the invented compliance surface was built to be plausible.
